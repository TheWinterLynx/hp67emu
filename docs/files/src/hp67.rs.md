# `src/hp67.rs`

## Purpose

Own the desktop-facing HP-67 live hardware machine and the small UI-to-hardware control translation layer.

## Why it exists

The desktop application must display and operate the same physical machine path proven by the headless milestones. Keys must not synthesize numbers or calculator operations in host code: the UI only closes and opens HP-67 key contacts, while firmware performs dispatch, stack operations, arithmetic and display updates.

## Relationships

Uses the versioned `Hp67Firmware`, `Hp67ArchitecturalMachine`, structural ACT/ROM display-fetch transport, `Hp67Keyboard`, ROM0 display decoding and the 1820-1749 cathode model. `KeyAction::physical_key()` converts the photographed panel identity into one of the 35 hardware contacts without assigning calculator semantics.

## Responsibilities

Maintain power/mode UI state; expose the fifteen physical LED segment slots; reset the structural live machine on power-on; drive the CRC external PROGRAM flag from the mechanical RUN/PRGM switch; expose the physical card-present contact and firmware-owned motor request at the live-machine boundary; own the nominal timed magnetic-card transport and advance it from the observed 320 us firmware word cadence; retain a live `Hp67Keyboard`; sample its held contact and latched code into ACT at each executed instruction boundary; continue executing firmware after the boot-idle checkpoint; and reject invalid UI digit identities instead of inventing a hardware code.

## Implementation

`Hp67LiveMachine::set_program_mode()` drives only the CRC external PROGRAM flag. M13 exposes the production `insert_magnetic_card()`/`take_completed_magnetic_card()` lifecycle around the timed transport; insertion drives external CRC card-present while firmware remains solely responsible for motor-on, write mode, buffer-ready sequencing and all card semantics. `Hp67LiveMachine::set_key_contact()` changes only the physical keyboard state. While a contact is held, `Hp67Keyboard::sample_into_act()` reasserts S15 before each executing word and preserves the latched keycode across release. The live machine no longer stops when it first reaches the firmware idle loop; `Idle` marks completion of boot validation while instruction execution continues. The live transport preserves the directly observed power-on exception: before firmware executes its first explicit display-control opcode, display serialization is permitted even though the architectural reset value of `display_enable` is false. After that first control opcode, the architectural DISPLAY latch owns whether ACT sends normal display data or the measured ROM0 blank code. A module regression boots the real versioned firmware, presses physical Digit1, observes firmware dispatch to 01440, releases the contact and requires the physical `1.` LED pattern. M12 adds a source-backed program-mode regression: RUN/PRGM transitions are considered settled only when firmware's internal S11 mode latch agrees at the no-key wait; PROGRAM key contacts are held through real `keys -> A` and `A -> ROM address` dispatch; every inserted step must advance the user-program counter in RAM `0x3D`; the first five stored bytes in RAM `0x2F` must be exactly `11 1B 12 37 00` for `1 ENTER 2 + R/S`; RUN-mode `h RTN` must clear RAM `0x3D` to step 000; and physical `R/S` must set S2 running, execute the stored program, clear S2 at the stored `R/S`, and stop on the canonical physical `3.00` frame.


M12 cycle-4430 correction: before calling the instruction-boundary architectural executor, the live machine now captures the serial pre-state used by both serial execution and same-word display traffic. The previously documented power-on display exception is applied to that pre-state, so later post-instruction A/B mutations cannot leak backward into b0..b7.


M12 cleanup audit: the power-on DISPLAY exception now clones architectural state only before the first explicit firmware display-control instruction; the steady-state live word path borrows the ACT state directly. The permanent PROGRAM regression reuses one physical firmware-dispatch helper, no longer builds per-cycle string traces or repeated heap-backed program-RAM snapshots on the passing path, and lives in the dedicated child module `src/hp67/m12_tests.rs` so the production-facing live-machine source stays focused.


M13 card-control regression: after the real firmware reaches its normal idle loop, asserting external card_present must carry execution through the main-loop card test and bank-1 card routine until firmware issues crc sf motor_on. The live machine advances Hp67CardTransport once per completed 320 us firmware word using the motor state that existed during that interval.

M13 magnetic media is now a complete Hp67MagneticCard rather than one detached side. Hp67LiveMachine::insert_magnetic_card() takes the physical card plus an explicit CardInsertionEnd. The transport resolves that end to Track 1 or Track 2, while the opposite track remains part of the same owned object and cannot be accidentally replaced during a pass.

The live head-switch sequence remains firmware synchronized. Insertion asserts card_present first; motor_on is firmware owned; the live machine observes the initial buffer_ready clears in Scr3341 before closing the modeled head contact. The transport then emits its startup-ready handshake and only after firmware acknowledges it does the nominal 28 ms record cadence begin.

Read and write regressions operate on recorded or unrecorded Hp67MagneticTrack objects. The 0x9B read path still proves that each CRC-visible 28-bit record reaches ACT C through real firmware. The 0x99 PROGRAM-mode write path writes only the selected track. A first write to TrackMedia::Unrecorded materializes recorded media, while per-track write protection raises CRC F7 without modifying that track.

The full-media regression writes 34 records to Track 1, extracts the completed Hp67MagneticCard, reinserts that same physical card through End1 and requires all 34 read words to equal the written sequence. Transport-level tests additionally prove that End2 selects Track 2 and that writing one track preserves the other track and its write-protect state unchanged.

After record position 34, the live machine deasserts card_present and opens the modeled head contact so real wait_no_card firmware can clear motor_on. take_completed_magnetic_card() then returns the same card to the host. Host formats and artwork are deliberately outside this API.

M13 two-track continuation: `HardwareDisplayFrame::shows_card_prompt()` recognizes only the physical segment triplet emitted by the real ROM0 path for `C`, `r`, `d` at the leftmost mantissa positions. `Hp67LiveMachine::card_prompt_visible()` exposes that observation read-only to the host. A regression forces program memory beyond step 112, writes Track 1, requires the real firmware `Crd` prompt, reinserts the same `Hp67MagneticCard` by End2 and requires Track 2 to be written with program header ID 4. `card_record_position()` exposes only the transport position so UI motion can follow the physical pass instead of a host timer.


`Hp67LiveMachine::card_write_mode()` exposes the CRC's firmware-owned write-mode flag read-only to the host so the UI can distinguish a `Crd` request for reading from one for writing. It does not set or clear the flag.


The two-track live regression now covers both directions. After real firmware writes header-3 Track 1 and header-4 Track 2 with a `Crd` pause between them, a fresh RUN-mode machine reads Track 1, reaches its own real `Crd` wait, receives the same card by End2, reads Track 2 and must restore the deliberately non-zero second-half program RAM register. This closes the same-card two-pass program path in both write and read directions.


M13 W/DATA coverage: a live regression reaches `W/DATA` through the physical `f` + `ENTER` keyboard path, first makes the secondary statistics registers non-zero with real `1`, `Σ+`, and then requires the firmware insertion prompt. The first pass must be header ID 1 (primary registers), real firmware must issue another `Crd`, and the same physical card reinserted by the opposite end must produce header ID 2 (secondary registers). A fresh RUN-mode machine then reads both passes, observing header 1, its own real `Crd`, and header 2 through `CrcDataRead`. This complements the program-card header 3/4 regression and covers all four documented card-header classes.

`withdraw_unstarted_magnetic_card()` is the live-machine boundary for removing a card that firmware has not started moving. It refuses once `motor_on` is asserted, the head is active, or any record position has advanced. On a valid withdrawal it deasserts the physical `card_present` contact before returning the same card to the host. This lets the UI recover from insertion while firmware is in `Error` without resetting or bypassing firmware state.

Power-cycle recovery: `take_magnetic_card_for_power_off()` deasserts the CRC card-present contact and returns any card still owned by the transport before the application rebuilds the electronic machine. `reset_power_on()` then reconstructs ACT/CRC/RAM/display/keyboard/transport state from defaults. A regression writes non-zero RAM, resets power-on and requires cleared RAM, blank reset display, no inserted card and card-present false.


M14B production DATA integration: the live machine now classifies only ACT RAM transfers whose selected address is actually installed in the temporary `ActRamImage`, snapshots the pre-instruction payload, and advances that payload through `Hp67DataSerialWordPath` from the same structural b0..b55 transport loop used for IS/display/fetch. The completed 56-bit frame is compared against the pending expected RAM payload and any mismatch is a hard live-machine error. Back-to-back transfers are supported because the previous frame completes at b1 while the next frame starts at b2. CRC/card ports are excluded by the installed-RAM check and remain owned by the separate CRC/card path.

This is a **WORKING APPROXIMATION** toward electrical RAM: it proves the source-backed logical DATA phase is preserved through real firmware without a second 56-bit loop. It still does not drive `Hp67Net::Data`, choose DATA polarity/passive bias, assign PHI-relative launch/sample edges, model propagation delay, or partition the temporary RAM image into physical 1818-* chips. Those details remain SOURCE-BLOCKED.


## M14C installed-RAM DATA authority

The live machine no longer allows the instruction-boundary ACT/RAM fallback to be the causal writer for installed-RAM DATA transfers. Before executing a RAM read/write-class word, the live bridge records the source-backed logical DATA payload and the addressed installed RAM slot. The architectural executor still runs as an oracle for the instruction's non-DATA effects and for the expected transfer value, but its C or RAM destination mutation is immediately restored. The destination is committed only from the 56-bit register reconstructed by `Hp67DataSerialWordPath`.

Because the directly observed DATA stream starts at b2 and finishes at b0/b1 of the following word, the pending frame tail is logically consumed before the following instruction-boundary fallback can depend on C or RAM. The shared structural loop then skips only those already-consumed DATA samples while still traversing the physical b0/b1 IS/display/backplane coordinates. This split does **not** claim a PHI-relative ACT register-write edge; it is the minimum scheduler bridge required to preserve the proven cross-word DATA phase while removing architectural RAM transfer side effects from the causal path.

Only addresses installed in the temporary `ActRamImage` use this path. CRC ports `0x99` and `0x9B` remain excluded and continue through the independent CRC/card model. DATA electrical polarity, passive bias, driver-enable timing, propagation delay and physical 1818-* partitioning remain SOURCE-BLOCKED.

## M14D serial arithmetic boundary authority

For ADD/SUB-family arithmetic, including destination-less compare operations, the instruction-boundary architectural executor no longer supplies the live machine's final A/B/C/carry result. The live machine records the pre-instruction A/B/C/carry state, runs the architectural path once as an oracle for the expected final arithmetic values and for still-unmigrated effects such as PC and instruction-state changes, then immediately restores only A/B/C/carry.

The same instruction then traverses the structural b0..b55 word. `ActSerialEndpoint` accumulates an `ActSerialArithmeticResultImage` from the selected digit results and carry/borrow chain generated by that traversal. After b55, `complete_serial_arithmetic_authority()` requires the structural image to match the architectural oracle exactly and only then writes that image into the live ACT state. A mismatch is a hard error with the executing word and both result images.

This deliberately preserves architectural effects that are not part of the migrated arithmetic result. In particular, compare instructions may put the ACT into `ThenGoto` through the architectural oracle while their carry/borrow result still comes from the structural image. Non-ADD/SUB arithmetic families such as clear/copy/exchange/shift and zero/nonzero tests remain architectural-fallback operations for now.

The final handoff after a complete word is a **WORKING APPROXIMATION**. It establishes causal authority for the final ADD/SUB A/B/C/carry result without asserting that the physical 1820-2530 writes an entire digit at b3 or commits registers on any particular PHI edge. Exact intra-word register and carry observability remains SOURCE-BLOCKED.

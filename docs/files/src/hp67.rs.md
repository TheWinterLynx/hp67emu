# `src/hp67.rs`

## Purpose

Own the desktop-facing HP-67 live hardware machine and the small UI-to-hardware control translation layer.

## Why it exists

The desktop application must display and operate the same physical machine path proven by the headless milestones. Keys must not synthesize numbers or calculator operations in host code: the UI only closes and opens HP-67 key contacts, while firmware performs dispatch, stack operations, arithmetic and display updates.

## Relationships

Uses the versioned `Hp67Firmware`, `Hp67ArchitecturalMachine`, structural ACT/ROM display-fetch transport, `Hp67Keyboard`, ROM0 display decoding and the 1820-1749 cathode model. `KeyAction::physical_key()` converts the photographed panel identity into one of the 35 hardware contacts without assigning calculator semantics.

## Responsibilities

Maintain power/mode UI state; expose the fifteen physical LED segment slots; reset the structural live machine on power-on; drive the CRC external PROGRAM flag from the mechanical RUN/PRGM switch; expose the physical card-present contact and firmware-owned motor request at the live-machine boundary; own the nominal timed magnetic-card transport and advance it from the observed 320 us firmware word cadence; retain a live `Hp67Keyboard`; sample its held contact and latched code into ACT at each executed instruction boundary; continue executing firmware after the boot-idle checkpoint; and reject invalid UI digit identities instead of inventing a hardware code.

## Implementation

`Hp67LiveMachine::set_program_mode()` drives only the CRC external PROGRAM flag. The M13 card-control regression drives external CRC flag 10 directly through the contained architectural machine and observes firmware-owned CRC flag 9; no production live-machine card API is exposed until timed transport and data ports are implemented. Firmware remains responsible for interpreting both hardware inputs. `Hp67LiveMachine::set_key_contact()` changes only the physical keyboard state. While a contact is held, `Hp67Keyboard::sample_into_act()` reasserts S15 before each executing word and preserves the latched keycode across release. The live machine no longer stops when it first reaches the firmware idle loop; `Idle` marks completion of boot validation while instruction execution continues. The live transport preserves the directly observed power-on exception: before firmware executes its first explicit display-control opcode, display serialization is permitted even though the architectural reset value of `display_enable` is false. After that first control opcode, the architectural DISPLAY latch owns whether ACT sends normal display data or the measured ROM0 blank code. A module regression boots the real versioned firmware, presses physical Digit1, observes firmware dispatch to 01440, releases the contact and requires the physical `1.` LED pattern. M12 adds a source-backed program-mode regression: RUN/PRGM transitions are considered settled only when firmware's internal S11 mode latch agrees at the no-key wait; PROGRAM key contacts are held through real `keys -> A` and `A -> ROM address` dispatch; every inserted step must advance the user-program counter in RAM `0x3D`; the first five stored bytes in RAM `0x2F` must be exactly `11 1B 12 37 00` for `1 ENTER 2 + R/S`; RUN-mode `h RTN` must clear RAM `0x3D` to step 000; and physical `R/S` must set S2 running, execute the stored program, clear S2 at the stored `R/S`, and stop on the canonical physical `3.00` frame.


M12 cycle-4430 correction: before calling the instruction-boundary architectural executor, the live machine now captures the serial pre-state used by both serial execution and same-word display traffic. The previously documented power-on display exception is applied to that pre-state, so later post-instruction A/B mutations cannot leak backward into b0..b7.


M12 cleanup audit: the power-on DISPLAY exception now clones architectural state only before the first explicit firmware display-control instruction; the steady-state live word path borrows the ACT state directly. The permanent PROGRAM regression reuses one physical firmware-dispatch helper, no longer builds per-cycle string traces or repeated heap-backed program-RAM snapshots on the passing path, and lives in the dedicated child module `src/hp67/m12_tests.rs` so the production-facing live-machine source stays focused.


M13 card-control regression: after the real firmware reaches its normal idle loop, asserting external `card_present` must carry execution through the main-loop card test and bank-1 card routine until firmware issues `crc sf motor_on`. The live machine now advances `Hp67CardTransport` once per completed 320 us firmware word using the motor state that existed during that interval. A dedicated regression loads a 34-record test side, enables the head gate, proves no record is emitted before the documented nominal 28 ms interval, then requires the transport to present record 0 and raise CRC `buffer_ready`. Architectural CRC `0x9B` read handling is implemented separately; UI-to-media lifecycle and the `0x99` write path remain pending.

# `src/hp67.rs`

## Purpose

Own the desktop-facing HP-67 live hardware machine and the small UI-to-hardware control translation layer.

## Why it exists

The desktop application must display and operate the same physical machine path proven by the headless milestones. Keys must not synthesize numbers or calculator operations in host code: the UI only closes and opens HP-67 key contacts, while firmware performs dispatch, stack operations, arithmetic and display updates.

## Relationships

Uses the versioned `Hp67Firmware`, `Hp67ArchitecturalMachine`, structural ACT/ROM display-fetch transport, `Hp67Keyboard`, ROM0 display decoding and the 1820-1749 cathode model. `KeyAction::physical_key()` converts the photographed panel identity into one of the 35 hardware contacts without assigning calculator semantics.

## Responsibilities

Maintain power/mode UI state; expose the fifteen physical LED segment slots; reset the structural live machine on power-on; drive the CRC external PROGRAM flag from the mechanical RUN/PRGM switch; retain a live `Hp67Keyboard`; sample its held contact and latched code into ACT at each executed instruction boundary; continue executing firmware after the boot-idle checkpoint; and reject invalid UI digit identities instead of inventing a hardware code.

## Implementation

`Hp67LiveMachine::set_program_mode()` drives only the CRC external PROGRAM flag; firmware remains responsible for interpreting that hardware input. `Hp67LiveMachine::set_key_contact()` changes only the physical keyboard state. While a contact is held, `Hp67Keyboard::sample_into_act()` reasserts S15 before each executing word and preserves the latched keycode across release. The live machine no longer stops when it first reaches the firmware idle loop; `Idle` marks completion of boot validation while instruction execution continues. The live transport preserves the directly observed power-on exception: before firmware executes its first explicit display-control opcode, display serialization is permitted even though the architectural reset value of `display_enable` is false. After that first control opcode, the architectural DISPLAY latch owns whether ACT sends normal display data or the measured ROM0 blank code. A module regression boots the real versioned firmware, presses physical Digit1, observes firmware dispatch to 01440, releases the contact and requires the physical `1.` LED pattern. M12 adds a program-mode regression that enters `1 ENTER 2 + R/S`, returns to RUN, clears X, returns the program pointer to 000 with RTN, starts with R/S and requires the stored program to stop on physical `3.00`.

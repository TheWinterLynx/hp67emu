# `src/hp67.rs`

## Purpose
Owns the remaining UI mechanical controls and a UI-local HP-67 structural machine whose LED state is derived from machine state, versioned real firmware and ACT-owned serial behavior.

## Why it exists
The frontend must expose hardware-derived behavior without formatting numbers or constructing display bytes. The photographed calculator begins in the physical OFF switch position: no firmware time advances and no LED emission is rendered until the user moves power to ON. Startup zeroes and the final `0.00` then emerge from ACT state, shared IS transport, ROM0 decoding and downstream cathode selection. The repository and released executable must both be self-contained.

## Relationships
`Hp67LiveMachine` uses the reusable `Hp67ArchitecturalMachine`, `ActSerialEndpoint`, shared display/fetch word transport, ROM0 decoder, 1820-1749 structural cathode driver and `Hp67Firmware`. The `hp67firmware.*` files are versioned directly with the project and compiled into the executable. `app.rs` advances the machine with elapsed wall-clock time only while `Hp67State.power_on` is true, and `panel.rs` consumes only raw segment masks.

## Responsibilities
Default the mechanical power switch to OFF; use the repository-versioned 5120-word `hp67firmware` image without runtime filesystem or network access; keep the display unclaimed during the pre-SYNC reset interval after an actual OFF→ON transition; bind each executing firmware word and its pre-instruction ACT state to the same complete b0..b55 structural cycle that fetches its successor; update each physical display slot only from ACT-owned bit serialization; consume ROM0 STR and ACT RCD downstream; and never synthesize startup or idle display values.

## Implementation
`Hp67State::default()` starts with `power_on=false`. `Hp67LiveMachine::power_on_default()` constructs `Hp67Firmware::default()` directly. The firmware data is brought into the executable with compile-time `include_str!`; there is no firmware pathname, environment variable, generated source or runtime firmware I/O. `app.rs` does not call `advance()` while the switch is OFF. An OFF→ON transition clears host timing and calls `reset_power_on()`, so reset hold, natural zero emission and firmware boot begin from cycle zero only when power is actually switched on.

At each firmware cycle the prefetched word becomes the executing word. Before architectural fallback semantics are applied, the live machine calls `ActSerialEndpoint::begin_execution(word, &state)`. The endpoint derives the pre-execution instruction state and captures immutable A/B/C/P/radix inputs before `Hp67ArchitecturalMachine::execute_word()` mutates the architectural machine. The following shared structural word advances that same execution through all b0..b55 coordinates and propagates ADD/SUB carry/borrow between selected four-bit digits. The machine verifies completion before accepting the next executing word. Reaching the no-key idle checkpoint no longer short-circuits the current structural word: the final active instruction first reaches b55, then the live machine enters `Idle`.

The display remains on the same transport. `ActSerialEndpoint` owns the 1..15 display phase, ROM0 owns STR and ACT owns the coarse RCD boundary. The cathode cannot choose what ACT emits. Architectural reset A=B=0 therefore naturally releases the display bits seen by ROM0 as zero under the weak-low IS bias.

The remaining ACT fidelity boundary is now narrower: execution has a full-word lifetime, immutable source state and source-backed digit-to-digit ADD/SUB chain. Destination A/B/C writes and exact intra-digit carry circuitry still remain behind the instruction-boundary architectural fallback until evidence fixes their physical bit/PHI timing. No PHI edge is fabricated by this slice.

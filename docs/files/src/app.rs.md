# `src/app.rs`

## Purpose

Run the desktop HP-67 application loop around the photorealistic panel and live structural machine.

## Why it exists

Input sampling, elapsed-time advancement and painting need one deterministic ordering. Physical key contact must reach the machine before the elapsed firmware work for the frame is executed.

## Relationships

Owns `Hp67State`, `Hp67LiveMachine`, the embedded front-panel texture, `Hp67Panel`, the small visual correction layers for top keys/sliders, the host magnetic-card object, and the program-card presentation state.

## Responsibilities

Create the versioned-firmware live machine; process power/mode switch events; reset on OFF-to-ON; continuously drive the live CRC PROGRAM input from the RUN/PRGM switch position; translate the panel's held `KeyAction` into a physical `Hp67Key`; release the machine keyboard whenever no key is held or power is off; advance firmware from real elapsed time; drive reader animation progress from the live transport's 34 physical record positions; recover the same physical card after a pass; expose the firmware-owned `Crd` prompt as the cue for opposite-track reinsertion; manage the passive-holder animation; and repaint continuously while powered or while a card phase is animating.

## Implementation

Auxiliary desktop surfaces are real child viewports, not `egui::Window` overlays inside the calculator viewport. `HP-67 Program Card Library` and `Save magnetic card` are created with `Context::show_viewport_immediate` and stable `ViewportId`s, so they can be moved, resized, focused, and closed independently of the calculator window. This is the desktop UI rule for future tool/viewer surfaces as well. The program-library viewport uses native top/bottom/side/central panels; its program listing lives inside a central two-axis `ScrollArea`, so long listings are clipped and scrolled within that viewport instead of painting past a parent-window rectangle.

Mouse key handling is physical-contact based rather than click based. `panel.rs` captures the key present on the primary-button down edge and keeps that exact contact asserted until the host primary button is released, even if the pointer drifts outside the original key rectangle; `app.rs` forwards the captured identity unchanged to `Hp67LiveMachine::set_key_contact()`. The A–E visual correction consumes the same contact identity, so visual and electrical release occur together.\n\nThe frame first paints the currently available hardware display and collects panel interaction. Mechanical events are applied, the RUN/PRGM state is passed to `Hp67LiveMachine::set_program_mode()`, the current key contact is passed to `Hp67LiveMachine::set_key_contact()`, then elapsed time is calculated and the live machine advances. Resetting `last_live_tick` on power transitions preserves the original zero-elapsed first powered frame. No UI key callback performs calculator-level work. `ReadingFromRight` no longer has a host-duration completion timer: its progress is `card_record_position / 34`, and the phase becomes `ParkedLeft` only when the live transport actually completes and returns the card.


M13 artwork loading: the exact HP badge is stored as `assets/hp67-card-logo.png`, cropped from the supplied original-card reference. `Hp67App` decodes it once at startup into a dedicated `TextureHandle` and passes that texture into the program-card renderer; the logo is no longer approximated with procedural line geometry.


M13 magnetic-media boundary: the app now owns an optional complete Hp67MagneticCard independently from the printed ProgramCardArtwork. Dropped .hpp files are decoded by TeenixHppImport in the host layer and merged into Track 1 or Track 2 according to the card header. Dropped .hp67raw and .hp67card images are also accepted directly. The reader itself never sees those file formats.

Reader clicks hand the complete card plus the current CardInsertionEnd to Hp67LiveMachine::insert_magnetic_card(). When the selected track has crossed the head, take_completed_magnetic_card() returns the same physical card object and the UI parks that returned object at the left exit. When the physical firmware display shows `Crd`, a single click on the card parked at the left exit rotates and immediately reinserts that same card through the normal right-to-left reader animation if the opposite logical track is valid for the current operation: recorded in read mode, or writable (including genuinely unrecorded media) in write mode. The UI does not synthesize the request for a second track: `Crd` is generated by real firmware. Outside that continuation state, double-click retains manual opposite-end selection behavior; a normal click still moves the card to the passive A-E holder.

The magnetic-media slot intentionally initializes empty until verified media is imported. The Moon Rocket Lander artwork is therefore never silently treated as recorded magnetic content.

Blank-card/write continuation: secondary-clicking the right reader hotspot requests a new unrecorded `Hp67MagneticCard` only when no host card is already prepared and no card is inside the live reader. The blank object is then inserted through the normal live-machine API; it does not pre-populate records or bypass firmware. During a firmware `Crd` continuation, read mode requires the opposite logical track to be recorded, while CRC write mode permits an unrecorded opposite track provided it is not write-protected. This is necessary for real two-track program writes, where Track 2 is commonly blank before the second pass.


Artwork/media identity: raw `.hp67raw`, `.hp67card` and newly created blank media use neutral card artwork. The SD-14A Moon Rocket Lander face is selected only when Teenix import metadata identifies the physical card as `Moon Rocket Lander` (case-insensitive, surrounding whitespace ignored). This prevents unrelated magnetic payloads from being visually mislabeled as the built-in Standard Pac card.


Card orientation is also passed to the presentation layer. `CardInsertionEnd::End2` still sets `ProgramCardView::rotated_180` for the magnetic-reader path and the left-exit card, so a same-card `Crd` continuation is visibly rotated while it is physically being read. The passive A-E holder is presentation-normalized: holder insertion and the final card-in-holder view always render the printed face upright. Logical insertion-end state is not changed by that visual normalization, so the next reader insertion still selects the correct magnetic track.

Host persistence is now available without adding a native-dialog dependency. `Ctrl+S` opens an independent native Save Magnetic Card viewport. The editable path accepts `.hp67card` for the lossless native container or `.hp67raw` when both tracks are recorded. Save is rejected while the physical card is inside the live reader, unsupported extensions fail explicitly, and `.hp67raw` propagates the media-layer error instead of inventing an unrecorded track. After `fs::write` succeeds, the same in-memory card is marked clean; write failures leave its dirty state untouched. Importing a card pre-fills the save path with the same basename and `.hp67card`, while a new blank card defaults to `hp67-card.hp67card`.

Blank-card and reader-entry recovery: a primary click on an empty reader slot now creates a new unrecorded `Hp67MagneticCard` and inserts it through the normal live API; primary click still inserts already prepared media when present. Every insertion enters `WaitingAtReader` first. The app moves to `ReadingFromRight` only after `Hp67LiveMachine::card_motor_on()` becomes true. If firmware does not start the motor (for example because the calculator is still showing `Error`), right-clicking the exposed waiting card calls the live withdrawal API and restores the same card to the host media slot instead of leaving it trapped at transport progress zero.

Power-off insertion guard: no host path may assert card-present while the mechanical POWER switch is OFF. `insert_current_card()` and `insert_new_blank_card()` both reject insertion when `Hp67State::power_on` is false, so imported media, blank media and `Crd` opposite-end continuation all share the same protection. The renderer also receives `reader_enabled=false` while OFF and changes the reader hotspot to hover-only with an explanatory hint.

Repeated blank-card replacement: secondary-clicking the free reader means "use a new blank physical card", not "only create one if no host card object exists". The request is accepted whenever the reader is physically free (`Idle`, `ParkedLeft`, holder insertion, or `InWindow`) and POWER is ON. A newly created blank replaces the previous host-side card object and is inserted through the same live firmware path. Waiting/reading phases still block replacement because a card is physically inside the transport.

Power-cycle boundary: HP documentation states that OFF->ON clears the loaded program and restores the calculator's default functions. The app therefore treats power-off as the end of all transient reader presentation state and power-on as a fresh `Hp67LiveMachine::reset_power_on()` electronic boot. The mechanical W/PRGM-RUN selector is not moved by software. If a card is physically inside the reader when power is removed, the transport returns that same card to the host before the electronic reset so imported media and already-written records are not lost.

Program Library: the desktop app exposes a Cards menu and an independent native library viewport backed by `PROGRAM_LIBRARY`. Loading an entry prepares one complete `Hp67MagneticCard` in the same host slot used by dropped files; it does not bypass reader insertion, firmware card detection, CRC transport, RUN/W/PRGM semantics, or opposite-end handling. A selected library index keeps the matching presentation metadata attached while that same physical card travels through the reader. Loading a dropped file or creating a blank card clears the library association. The library window is now split into a pack browser and a listing pane. Each PAC is an egui collapsing section closed by default, with its program cards selectable underneath. The right pane shows the selected card metadata and a monospaced listing decoded from its checked-in magnetic payload, including raw internal byte values; two-part continuation cards show side boundaries and step 113 onward where the firmware header identifies a continuation.

PDF-derived artwork is embedded presentation state for every Standard Pac and Games Pac catalog card whose checked-in pack PDF provides the physical face. `assets/hp67-card-artwork-atlas.png` contains 35 source-faithful rows (15 Standard Pac + 20 Games Pac) normalized to a 499×80 atlas cell whose aspect follows the physical 71.1×11.4 mm card instead of the earlier 480×80 approximation. The extraction tool keeps the PDF artwork at native DPI, anchors the stable top/left card registration, fills missing right/bottom source area with the canonical black card substrate, crops only source overflow, and uses the exact chamfered geometry while normalizing the source. Compact top registration/index blocks are detected geometrically before edge cleanup; PDF/page fringe is then removed independently and the detected blocks are repainted solid white. This avoids the earlier failure where a one-pixel white page connection could make a legitimate block look hollow or disappear. The canonical face is then flattened onto fully opaque black before downsizing to the 499×80 atlas with BOX area sampling. The UI polygon owns the visible chamfer, so PNG transparency can no longer expose bright calculator-photo pixels. A concrete SD1-01A regression also requires bright pixels in the two Moving Average top blocks so the previously hollowed marks are caught by the Rust gate. The app validates and decodes that atlas once at startup, crops the row selected by `ProgramLibraryEntry::artwork_atlas_row()`, and uploads that exact face as the card texture when the library entry is loaded. A corrupt or dimensionally invalid artwork atlas is presentation-only failure: it is logged and disabled rather than panicking the calculator process, while a unit regression explicitly requires the checked-in atlas to decode at test time. The texture follows the same reader rotation and upright-holder rules as other card faces and never alters magnetic bytes. The legacy per-file `artwork_path` is only a fallback. Demo Pac 1 remains procedural/generic because no verified Demo Pac PDF is checked in, rather than fabricating a card face. The library reports the source PDF and marks atlas-backed entries as embedded card crops.


WASM host timing: the front-end wall-clock fields use `web_time::Instant` rather than `std::time::Instant`. This keeps the existing elapsed-time ordering and animation semantics on native while using the browser's monotonic clock on `wasm32-unknown-unknown`. This change is confined to the presentation/pacing boundary; deterministic calculator timing remains inside `Hp67LiveMachine` and the emulation core.

The first WASM slice intentionally preserves the native filesystem import/save code unchanged. It is expected to compile for wasm but browser filesystem persistence is not claimed by this slice; built-in program media and embedded artwork remain available because they are compiled into the binary. Browser-native card import/export is a follow-up host-adapter task, not a calculator-core change.


WASM viewport adaptation: browser builds must not use `Context::show_viewport_immediate` for the Program Library or Save Card surfaces because eframe web cannot provide independent native child windows. On `wasm32`, the Program Library is therefore an ordinary movable/resizable `egui::Window` with both title-bar close control and an explicit `Close` button; a successful `Load card` also closes it immediately so the calculator becomes visible again. The native build retains the independent child viewport implementation unchanged. The browser Save Card surface is likewise a closable embedded window and explicitly reports that browser export is not implemented yet instead of attempting a native path write.

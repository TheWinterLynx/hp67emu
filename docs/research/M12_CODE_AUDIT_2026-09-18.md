# M12 code audit — 2026-09-18

## Scope

This review audits the current `agent/m12-program-entry-execution` branch after the end-to-end regression for:

`PROGRAM: 1 ENTER 2 + R/S -> RUN -> RTN -> R/S -> physical 3.00`

passed together with the full library and `hp67emu` binary test checkpoint.

The audit is deliberately separate from the earlier source/fidelity investigations. Its purpose is code quality: remove temporary debugging scaffolding, eliminate avoidable work in the live path, consolidate duplicated test logic, check that comments still describe the implementation, and verify that the M12 milestone status is not overstated.

## Functional baseline retained

The cleanup must preserve all of the following M12 evidence:

- the mechanical RUN/PRGM switch drives CRC external flag 1;
- firmware, not host code, owns the internal S11 PROGRAM latch;
- physical key contacts execute real `keys -> A` followed by `A -> ROM address`;
- PROGRAM entry changes real HP-67 program RAM and advances RAM `0x3D`;
- steps 001..005 are stored exactly as bytes `11 1B 12 37 00`;
- RUN-mode `h RTN` clears the user program counter to step 000;
- physical `R/S` sets S2 while running;
- the stored `R/S` clears S2 and halts;
- the physical LED frame is `3.00`;
- RAM `0x3D` advances to the step-006 encoding `[F,2,1]`.

No cleanup in this audit weakens any of those oracles.

## Findings and corrections

### 1. Avoidable ACT-state clones in the live word path

M12's power-on DISPLAY exception originally cloned the complete `ActArchitecturalState` unconditionally in two places on every word:

1. before binding the serial pre-instruction execution snapshot;
2. before the shared display/fetch transport.

Those clones were needed only while the architectural DISPLAY reset value is being overridden before firmware executes its first explicit DISPLAY-control instruction.

Corrected in commit `f34a31b`:

- once `display_control_seen == true`, both paths borrow `self.machine.act.state` directly;
- a temporary cloned state is created only during the short power-on exception window;
- the behavior of that exception is unchanged.

This removes two unnecessary full-state copies from the normal steady-state word path.

### 2. Duplicated PROGRAM/direct-key dispatch harness

The M12 PROGRAM helper contained a second copy of the same firmware-dispatch state machine already needed for RUN-mode keys:

- hold physical contact;
- observe real `keys -> A`;
- verify the physical scan code;
- observe real `A -> ROM address`;
- release the contact;
- return the actual firmware target.

Corrected in commit `e6ced0a`:

- one `press_live_key_to_dispatch()` helper now owns that sequence;
- exact-target checks are layered by `press_live_key_to_expected_dispatch()`;
- PROGRAM mode reuses the same helper and applies only its source-backed unshifted-table range oracle.

This removes duplicate control-flow code while retaining different PROGRAM and RUN assertions.

### 3. Temporary diagnostic allocations remained on the passing path

During M12 debugging, `press_program_key_and_require_ram_change()` accumulated:

- up to 96 formatted control-trace strings per key;
- formatted RAM-operation trace strings;
- a fresh 32-register program-RAM snapshot on every settle cycle;
- a newly allocated vector of changed register addresses on every settle cycle.

Those diagnostics were useful while locating the faults but were no longer appropriate in the permanent passing regression.

Corrected in commit `e6ced0a`:

- the temporary string traces are gone;
- program RAM is snapshotted once before and once after each inserted key;
- the snapshot is a fixed-size array rather than a heap `Vec`;
- settle loops inspect only the state required for the oracle;
- failure messages retain the key target, firmware PC and relevant state without continuously building trace text.

### 4. Magic loop bounds

The M12 harness repeated literal limits such as `512`, `4096`, `8192` and `20000`.

Corrected in commit `e6ced0a` with named constants for:

- key dispatch;
- firmware settle;
- mode-switch settle;
- stored-program execution.

The limits and behavior are unchanged.

### 5. Stale display-transport documentation

`begin_display_fetch_cycle()` still stated that b0..b7 read live A/B on each bit. That was no longer true after the cycle-4430 fix: executing words use the immutable pre-instruction serial snapshot, while only fetch-only words use the supplied live architectural state.

Corrected in commit `6c02ab4`.

Related live-cycle error messages were also changed from `live boot cycle` to `live cycle` where the same code now runs after boot during keyboard and program execution.


### 6. M12 regression code mixed into the live-machine module

The end-to-end M12 harness had grown large enough to obscure the production-facing implementation in `src/hp67.rs`.

Corrected after the initial cleanup:

- M12-specific tests, constants and helpers now live in `src/hp67/m12_tests.rs`;
- the child test module retains private access to the live machine, so no production API was widened for tests;
- `src/hp67.rs` keeps only the generic live-machine tests and production implementation;
- the new Rust file has the required companion documentation and is indexed in `docs/FILES.md`.

## Intentional behavior retained

The following may look more complex than a minimal emulator, but are intentional fidelity boundaries rather than cleanup debt:

- `step_firmware_cycle_with_execution()` exposes the exact word that executed in the current pipeline cycle so tests do not infer execution from stale latch state.
- Unknown ACT display modifiers remain hard errors.
- Unknown ROM0 classes such as `$5x` remain hard errors.
- The ROM0 decode diagnostic reconstructs pre/post A/B only inside the error path; it has no normal-path formatting cost.
- The display byte is still generated bit-by-bit through the structural IS transport rather than replaced by a host-side formatted value.
- RUN/PRGM is still a hardware flag input; no UI-side PROGRAM semantics were added.

## Performance boundary outside this M12 cleanup

`Hp67ArchitecturalMachine::execute_word()` currently clones the architectural machine to provide rollback on execution errors. That cost predates M12 and is not changed here because replacing it safely requires a separate transactional/error-semantics review.

Likewise, ROM0 display encoding is evaluated through the bit-serial transport. Caching or collapsing that work solely for speed would need to preserve the project's future intra-word timing model and is therefore not done as an opportunistic M12 optimization.

## Milestone-scope audit

The active integration roadmap defines M12 as:

- RUN/PRGM hardware flag;
- program entry;
- editing;
- stepping;
- execution.

The current branch now has strong end-to-end evidence for the hardware flag, entry and execution portions.

It does **not** yet contain an equivalent functional proof for PROGRAM editing and single-step/back-step behavior. M11 proved direct/shifted keyboard dispatch broadly, but dispatch alone is not enough to claim the M12 editing/stepping semantics.

Therefore the roadmap is corrected to **M12 in progress**, with the current program-entry/execution slice complete. M12 should be marked fully complete only after editing and stepping receive source-backed firmware regressions of comparable strength.
